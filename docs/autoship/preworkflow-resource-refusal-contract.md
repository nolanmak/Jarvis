# Pre-workflow resource refusal reporting

Issue #1957, under #1706 / #1714 / #1703. Design checkpoint only; not deployed.

Parent: #1706; reporting #1714; recovery #1703. Capacity sizing remains #1917.

PR #1956 reproduces a command accepted and selected, then deferred before workflow creation. Its durable status says only `execution-readiness-blocked`, while the worker logs `workflow-resource:capacity-exhausted`. The original numeric refusal is lost. #1915 preserves an existing checkpoint blocker; this case has no checkpoint. Evidence: #1706 comment 6754725023 and docs PR #1916, commit 64689d12.

Required behavior:
- Preserve the original controller-produced resource refusal as bounded, typed observational data for the selected command attempt, without a model call, workflow registration, new reservation or reconstructed probe. Keep the existing high-level reason/exit semantics.
- Bind diagnostic persistence to the original workflow/selection and fenced terminal update; delayed/duplicate completions cannot overwrite another attempt. New selection cannot present an older refusal as current. Stores without the added data remain readable without read-side schema writes.
- Project the same sanitized resource code and numeric facts to CLI and the existing private progress route, including when no workflow exists. Owner pause and authorization failures retain priority. Do not serialize policy bodies, paths, error text, credentials or arbitrary provider output. Unknown data remains unknown.
- Preserve atomic command completion/outbox projection, unchanged-blocker deduplication, five-minute unpaid retry, queue fairness, original request and full execution admission. This is reporting, not a capacity increase, execution grant, merge proof or claim that Autoship is restored.

Test-first exits:
1. Reproduce information loss against unchanged production code using a real disposable store and an actual resource-preflight error carrying a scripted controller observation. Assert the expected sanitized code/facts survive completion, reopen, status and private projection before a workflow exists.
2. Cover old-schema read-only compatibility, replacement selection, stale/duplicate completion, owner pause/authorization priority, malformed/unbounded/private observations and rollback when projection fails. Verify zero model admissions and unchanged allowance.
3. Implement, run the affected managed suites and required hosted checks; attach tested heads, real failing/passing assertions and limits. Independent exact-head approval, normal updater rollout and a live command/private-delivery observation remain separate gates.

This issue tracks an existing S/H requirement; it does not close the automatic-sizing design, retained-runtime custody, retry lifecycle or full #1703 acceptance.

## Exact delivery decisions

D1 — Ownership and producer. The existing command job identifier exists before the execution workflow row. Its latest scheduling turn is `command_attempt(workflow, selected_at)`; `next_command_job` creates/replaces that turn and its five-minute schedule. The worker obtains the resource `Readiness` in `execution_preflight`; `preflight_selected_resources` consumes that same report. Attach a sanitized observation to that error before the report is dropped, using an anyhow error context distinct from `CommandFailure`. Do not re-run inspection or parse Display text. The outer `CommandFailure` remains code 3 / `execution-readiness-blocked`. Preserve all earlier runtime/provider and later deployment gates. Other errors get no fabricated resource observation.

D2 — Exact observation. Version 1 contains `status` and optional `refusal`. Accept only a controller observation whose `status` equals the original Readiness status, `permits_attempt` is false and `live_verified` is false. Allowed statuses: `declaration-invalid`, `declaration-exceeds-service`, `delegation-unavailable`, `inspection-busy`, `capacity-exhausted`, `inspection-unavailable`. A refusal, if present, requires phase `admission_failed`, exhausted true and one code below. Copy only these code-specific unsigned u64 facts (bytes are bytes, PIDs are counts, CPU percent is percent, CPU quota/period are microseconds); unknown keys are discarded:
- host_headroom: requested_bytes, reservation_slack_bytes, margin_bytes, required_bytes, available_bytes.
- aggregate_reservations: requested_bytes, reserved_bytes, current_bytes, reclaimable_bytes, limit_bytes.
- ancestor_headroom: requested_bytes, reservation_slack_bytes, current_bytes, limit_bytes.
- declared_ceiling: requested_bytes, limit_bytes, requested_pids, limit_pids, requested_cpu_percent, limit_cpu_quota, limit_cpu_period.
- invalid_policy: memory_bytes, pids, cpu_percent, minimum, maximum.
- admission_setup_failed: no numeric facts; optional errno u64 in 0..4095 and optional failure_class from RuntimeError, ValueError, TypeError, JSONDecodeError, OSError, FileNotFoundError, PermissionError, BlockingIOError, NotADirectoryError, TimeoutError, BoundaryFailure. These two fields are absent for other codes.
A present allowed fact with the wrong type/range, unknown code/status/phase, contradictory flags or malformed refusal invalidates the entire optional observation: finish the original deferral with no observation. Missing facts are unknown, not zero. No strings from policy, paths, Display/Debug, arbitrary output or unknown keys cross this boundary. Serialized observation is at most 1024 bytes; reads reject unknown fields, wrong version or invalid content. A host_headroom example is status capacity-exhausted, phase admission_failed, exhausted true, required_bytes 6710886400 and available_bytes 6375665664. Changing available_bytes to a path, negative number, boolean or u64 overflow yields no observation.

D3 — Storage and fence. Add one optional latest-observation row per command job in the existing workflow database, owned by WorkflowStore initialization. Row identity is workflow plus selected_at, referencing the existing command attempt owner; payload is bounded <=1024 bytes. Initial installation uses normal write-side schema initialization only. Old stores missing the table read as no observation; read-only status performs no migration. Normal write-open installs the table before completion. Finish remains conditional on matching workflow/selected_at and finished_at IS NULL; only a deferred `execution-readiness-blocked` result can carry the observation. Update attempt, replace observation and project progress in one existing transaction; any failure rolls all three back. Late/duplicate completion changes nothing. A new selection deletes the old latest-observation row atomically with replacing the attempt. No historical observation table or new allocator is introduced. Missing table on a writer outside supported initialization is an error, not silent loss.

D4 — Lifecycle and visibility. The latest CommandAttempt gains optional resource_refusal with serde default for old payloads. Status exposes the bound observation only for the matching finished deferred readiness attempt; selection has no receipt. Its sibling selected_at/finished_at label its age. Pause hides the current resource blocker; any previous completed attempt remains explicitly historical in last_attempt. Authorization failure/success/other outcomes cannot carry a current receipt. New selection clears it, and later completion replaces it. Clearing pause does not resurrect deleted data; an unchanged latest completed attempt may become visible again, labelled with its original timestamps. Progress carries a bounded observation plus original attempt selected/finished timestamps and describes it as the last observed attempt, never live readiness. Owner pause, authorization rejection and terminal workflow/merge state take precedence and suppress the resource projection. Old progress payloads deserialize with no resource observation. CLI JSON, text status, private progress and private status command use the same safe observation/rendering helper; JSON keeps typed facts and messages render that same data, within existing message bounds. No public Discord destination is added.

D5 — Deduplication and observation freshness. Blocker identity is status plus refusal_code plus requested demand/declared limits (requested_bytes, required_bytes, margin_bytes, requested_pids, requested_cpu_percent, limit_bytes, limit_pids, limit_cpu_quota, limit_cpu_period, memory_bytes, pids, cpu_percent, minimum, maximum). Times and changing usage/free/reserved/reclaimable/slack values are observations, not a new blocker identity. A new code/demand/limit changes the progress fingerprint; repeated identical identity updates latest persisted progress payload and CLI facts without emitting a new progress event/notification. Existing immutable event/delivery content remains the original observation with its original attempt timestamps. A newer observed payload is not proof that an earlier delivery sent updated numbers. Existing eligibility/backoff, provider accounting, owner controls and progress/merge precedence remain authoritative.

D6 — Readiness scope. This component implements the reporting boundary in #1706/#1714 only. It never grants capacity, shrinks demand, changes resource limits, modifies an allowance, registers a workflow to report a failure, resumes held work or establishes teardown. Exact live refusal/rollout/private delivery require observation after normal review/deployment; passive reference vectors do not substitute for them.

Design checkpoint: fresh-reader, conversation/source comparison and all 12 mapped seams checked. Six initial findings were resolved and rechecked. Design consistency does not establish code correctness or independent approval. Behavior tests, implementation, hosted checks, normal rollout and actual command/private delivery remain pending. Full automatic sizing and integration remain owned by #1917.
