# Private owner publication and recovery protocol

Status: proposed implementation protocol for P1/P2 of [owner acceptance publication](owner-acceptance-publication.md). The overall P1/P2 implementation remains incomplete and productive owner ingress is unconnected; the component checkpoints below describe partial implementation. D/#1713, T/#1712 and R/#1676 own the join; the existing P3–P5 and C/R execution requirements remain gates. This document extends the existing workflow/native/acceptance services; it introduces no alternate verifier or merge authority.

## 1. Authority and ordering

An accepted owner message, an independent preparation, an activated registration, a published canonical manifest and permission to execute are different facts. None implies the next one. The existing canonical manifest and registered verifier map remain the acceptance source. A publication journal records how that source changes, not whether code passes.

Private activation must atomically record the immutable publication intent with the preparation/baseline, activation, generation fence and review invalidation. No new private activation may commit without its intent. Existing activation history without publication remains inspection-only; absence does not grant a legacy exception to owner coding.

Before that transaction, the producer persists the exact next `PreparedAcceptance` as immutable private evidence. This file is not active until the canonical manifest references it and publication is completed. The old canonical namespace is resolved before preparation: an orphan original baseline must be recovered or refused, never ignored as an absent original contract. An initial activation requires an actually absent original acceptance; a revision requires the exact existing registration and manifest.

The normal path is:

1. Authenticate current owner/repository authority and acquire the exclusive owner turn using the shared service. Its generation fences prior guards; unsettled turns prevent ordinary takeover.
2. Independently prepare and reproduce acceptance, retaining the complete original request and protected bytes. Persist immutable next evidence under current metadata admission.
3. In one immediate workflow transaction, recheck the exact old manifest and evidence, original preparation, turn/control revision and candidate; persist intent, activation and generation fence together.
4. Finish original-store native handoff and establish actual native/resource quiescence. Reconcile an existing native transfer rather than creating a replacement transfer ID.
5. Under original native proof, acquire the write-scope lock, then the immediate workflow transaction. Recheck the intent and old-or-next canonical bytes, conditionally bind the exact scope, publish the exact next manifest, fsync, and atomically record publication completion/remove the active pending pointer.
6. Expose a productive owner guard only after all publication, native, scope, source/resource, authorization and output gates pass. Reserve the coding body once at its native input boundary; then execute it through the actual pinned provider conversation.

The lock order for the proof-bearing commit is original native state/session/audit locks, write-scope lock, workflow transaction, then bounded protected-file operations. No transaction or workflow mutex is held while acquiring native/session/audit/scope locks, awaiting a provider, querying GitHub or waiting for a subprocess. Native proof callbacks may make short workflow accesses; those accesses must not reopen the held native/audit locks. Existing ordinary scope writers must join the same scope-lock/workflow ordering. A validation before entering a scope writer is insufficient.

The existing synchronous metadata visitor remains the file admission primitive. Its ordinary form rejects private publication pending/blocked state. Private publication/recovery uses a separate writer capability tied to the exact intent and fresh original native proof. It is not an `ignore_pause`/`skip_publication` flag and cannot authorize model calls.

## 2. Immutable journal and canonical files

Add immutable publication history keyed by the existing owner `request_id`, an active pending pointer with at most one entry per workflow, and immutable completion/disposition records. Each history row is joined bidirectionally to its event by a digest. Removing a pointer never removes the history or makes an uncompleted activation productive.

The version-1 intent binds:

- Canonical repository/workflow/source and the authenticated message ID/body digest.
- The exact original `Input` and `CandidateIdentity`, original input-context hash and `OwnerPreparationBinding`.
- Original and activated generations, previous/next bindings and immutable registration references/digests, and original native registration/binding references.
- Exact previous manifest bytes/digest or proven absence, exact next manifest bytes/digest, and the next evidence basename/length/digest.
- Original preparation artifact reference and immutable input/candidate data sufficient to validate its existing version-2 envelope; no newly derived recovery context key.

Use strict typed schemas, canonical existing serialization and lowercase SHA-256. Unknown fields/versions refuse. The intent is at most 4 MiB plus 32 KiB: original input/candidate data is bounded by the original 4 MiB envelope, with bounded manifest/reference overhead. Registrations are referenced, not duplicated into this envelope. Manifest byte strings are at most 4 KiB each and next evidence/preparation retains the existing 4 MiB bound. Refuse oversize before activation without truncating requirements. Large private data stays out of the bounded event payload: events carry the record digest and identifiers. Journal/evidence/native references count toward protected storage admission and retained history bounds; they are not evictable retry caches.

The next evidence basename is `SOURCE-owner-REQUEST_SHA256-revision-REVISION-CONTRACT_SHA256.json`. It contains only the exact prepared acceptance, in the existing controller-private canonical namespace. No adapter is installed into product Git. The original preparation and canonical evidence are distinct immutable records with an exact digest relationship; neither is a second verdict engine.

Ready completion binds the intent digest, actual native handoff/quiescence references, actual registered scope reference, canonical/evidence digests and current recovery lineage if any. A `published_ready` completion is descriptive history, not permission to skip fresh scope/source/native checks later. Blocked observations are separate append-only dispositions, not completion: they retain the active pending pointer and name observed scope/canonical/native facts, missing proof and required recovery action. No new canonical manifest is published without the scope proof required in §1. If the exact next manifest already exists but its prior scope effect is now unprovable, retain it as uncompleted metadata and block productive reads.

Productive canonical reads distinguish original evidence, completed ordinary amendments and completed owner publication. An ordinary amendment descending from an owner publication must validate its old manifest-history chain back to that completed publication, preserving every required criterion. It must not mistake the owner evidence filename for an ordinary amendment completion. Old loaded consumers and ordinary acquisition must validate this canonical lineage before dispatch; `inputs_changed` must not overwrite accepted criteria from stale issue/title data. Independently authorized ordinary amendments remain supported.

## 3. Productive and metadata capabilities

Productive dispatch, model charging, body reservation, publication and merge admission all consult one publication predicate in their normal workflow transaction. Pending/blocked publication, an uncompleted private activation, stale canonical lineage or an active metadata-only recovery lease refuses. The same predicate must cover retained/cached guards and observer callbacks; checking only when reading a manifest does not fence an already-loaded consumer.

Native setup/reconciliation cannot use that productive predicate: it must finish the work that will satisfy it. Introduce a private, nonserializable metadata authority with exactly three variants: `LiveOwnerTurn`, `RecoveryLease` and `TerminalCheckpoint`. The uninterrupted activation path mints `LiveOwnerTurn` from the consuming original guard/preparation after the intent/activation transaction, binding its current activated lease, exact intent and original native registration. No recovery lease is fabricated for this path. The other variants validate the current recovery lease or existing terminal-native checkpoint and the same original lineage/registration. Each authorizes only inspection, original transfer settlement, scope/metadata commit and result settlement for that intent. It never installs an executable reasoner or an ordinary model observer. Its audit/model dispatch is denied, including after pending input becomes applied. Productive callbacks are installed only by the separate post-publication productive constructor.

The original opaque preparation and live body-dispatch capability remain required for coding. Publication rows and native session strings cannot reconstruct them. A recovery producer may reopen the exact original preparation only through authenticated lineage plus fresh original native proof; it cannot derive a new context filename from the recovery generation or reinterpret old preparation-free history as ready.

Required native producer contracts, before a journal writer is enabled:

- A borrowed original-native quiescence capability: validates original store/epoch, actual namespace/session/resource inventory and selected policy, retains the original locks through its visitor, and refuses unknown cleanup. A saved scan or receipt alone cannot construct it.
- A scope mutation capability: holds the actual registered scope lock, compares old/next contract and permission bytes, and does no native I/O while the workflow transaction is held.
- A native invocation input boundary: resource/configuration admission precedes body reservation; the trusted native path links exact prompt digest, request/preparation and dispatch to the original native invocation before releasing input. Provider code cannot consume an unrecorded body grant.
- A verified native outcome/reconnect capability: inspects the actual retained original invocation/conversation under original locks, not a PID, path, model response or claimed session ID. Complete and interrupted/restorable outcomes are distinct. Missing support for a provider/version holds instead of creating a new conversation.

These extend the existing native ownership/resource services. They are implementation requirements, not claims that the current APIs already supply the capabilities.

## 4. Recovery lease and immutable lineage

Routine recovery runs through the shared unpaid reconciliation service. It reauthorizes the immutable owner/private origin and repository, preserves provider pin/authorship, and selects the existing request/intent. A live current lease defers; lease expiry alone never grants execution.

For a nonterminal interrupted turn, a separate CAS claim creates a new **metadata-only** recovery generation. It retains the original request, original input-context key, activation fence, preparation, body reservation and native namespaces in immutable lineage. It does not rewrite the original activation generation. Every recovery attempt records its predecessor lease/generation and intent digest; only one current attempt may settle. Reconnection can inspect/reconcile the original native transfer before creating any new transfer. Ordinary claims remain blocked while the original turn/recovery is unsettled.

The recovery lease may settle already-approved metadata while an explicit owner pause, newer queued input or another workflow hold exists. It cannot clear that control or run a verifier/model/candidate mutation. It reads the latest control/terminal state again at each commit and records it. Current publication/execution authority requires current authentication; revoked/mismatched owner or repository authority holds publication. Existing trusted resource cleanup still owns verified teardown and retention without sending private data to a new owner/destination.

After metadata settlement, a distinct productive guard acquisition needs a new generation, fresh native handoff, current unpaused authorization, valid canonical acceptance, actual scope/source/resource admission and all normal gates. It validates an immutable bridge to the **original** input/preparation. A later generation does not pass the old `original + 1` rule merely because it is newer. The recovery lease and audit object never become that productive guard by clearing a flag.

The transfer to that constructor is explicit. Under one CAS transaction on the current recovery lease and exact intent/turn:

- A proven completed body with durable response settlement applies only its captured message and sets the original turn `completed`; later messages remain pending. Recovery releases its lease after native settlement, so ordinary admission or the next message's owner-turn admission can run normally.
- A still-pending request with ready publication records an immutable `OwnerSuccessorReady` bridge and changes the original turn to `recovery_ready`, without applying its message. The common bridge fields contain original input-context/preparation and activation identities, settled recovery/native generation, target binding and scope/native settlement references. Its execution plan is a strict tagged union. `unexposed_body` carries the original-native setup/nonrelease proof reference and an optional existing original dispatch reference; it requires no coding-conversation frontier because a coding invocation may not exist yet. `continue_original_conversation` requires the original exposed dispatch and actual restorable coding-conversation frontier proof. Preparation/scoping conversation progress cannot satisfy that field. Unexposed requires fresh original-native proof of no body input release; absence of an SQL reservation alone is insufficient. The bridge stores references, never executable proof; the corresponding native producer must revalidate them when its successor constructor runs.
- The transaction terminates/releases the metadata recovery lease and preserves the workflow checkpoint/control. `recovery_ready` remains an unsettled state: ordinary claims and the generic next-message owner claim refuse it. Extend the one-active-turn constraint accordingly. Neither `completed` nor `setup_refused` is synthesized to escape those guards.

Only `claim_recovered_owner_turn_for_setup` may CAS-consume that exact bridge for the same pending request, after current owner/origin/repository checks and an unpaused control. It advances generation again, records the immutable successor edge, and changes the projection to `claimed` with the new lease owner/revision/binding. It does not replace original input or the activation fence. The setup constructor performs fresh original-store handoff and all execution gates before any model/input permit escapes. `unexposed_body` without a prior reservation may use the first-reservation factory at the native input boundary. With a prior reservation it must use the distinct recovered-unexposed constructor in §5, preserving that reservation; neither branch reconstructs an old body capability. Continuation may mint only a new continuation capability. A failure before exposure may return to readiness only through an actual constructor-owned unstarted-setup proof. Partial native effects or an escaped guard return to metadata reconciliation instead. A pause before successor claim leaves the bridge/input intact; queued peers do not become implicitly applied or overtake the retained active request. Terminal state or changed authority prevents successor execution.

Terminal merged/retired workflows use the existing terminal-native checkpoint for observation/cleanup, rather than resurrecting an execution lease. Late native outcomes can be recorded truthfully without changing terminal state, counting another shipment or starting post-merge coding.

## 5. Body outcomes and continuation

Move resource/configuration admission before the once-only body reservation at the trusted native input boundary. Preflight failures before that boundary retain input and budgets without creating a falsely exposed body. A reservation/response row is never permission to send the body again.

### 5.1 Reserved but unreleased input

The request retains exactly one immutable body reservation. Do not delete, retire, replace or rewrite it to recover unsent work. Introduce a distinct non-cloneable/nonserializable `RecoveredUnexposedBodyDispatch`, constructed only by `with_recovered_unexposed_owner_body`. It is not an `OwnerBodyDispatch` deserialized from history. Its borrowed visitor retains original native/input locks, fresh successor authorization and the exact original preparation. The constructor validates the original reservation/event, original request/body/preparation/provider, immutable successor edge and current canonical/scope/source/resource admission. The original reservation may name an older generation; history readers validate its original immutable turn/activation plus explicit successor lineage, rather than comparing it to an overwritten current-turn projection. Missing halves never infer this relationship. Existing version-1 records without the required native input-boundary history remain unprovable for automatic recovery.

Fresh `NativeBodyNonreleaseProof` must establish that this exact original body has never crossed the trusted input boundary and that no original process, retained descriptor, queued transport write or old capability can subsequently release it. It binds the original store/epoch, request/preparation/body digest, reservation when present, every associated prepared launch and the exact revoked release authority. It requires the native producer's locked release ledger and actual resource/quiescence evidence; SQL absence, empty transcript, missing reply, timeout and `UnusedNativeOwnerProof` alone cannot mint it. Transfer fences release authority at the actual input writer, not only at the controller observer. An original unexposed prepared invocation is reconnected or verifiably settled before another setup is admitted; no parallel replacement is created from uncertain effects.

Under those held native locks, one immediate workflow transaction validates the exact already-consumed ready bridge and its current successor claim from §4, CAS-claims that successor's distinct release-authorization slot and records an immutable recovered-release authorization edge from the original reservation to the current successor/input-boundary attempt. It does not consume the ready bridge a second time. The slot is unique per successor and body reservation; its creation/consumption and the edge/event commit atomically. A crash after successor claim but before slot creation returns through metadata reconciliation after the lease is no longer live: it validates the immutable successor edge and obtains fresh nonrelease/setup proof, then produces a new ready bridge and successor. The old ready bridge is never consumed again. If native setup may have escaped, the ordinary unknown-effects hold applies until the original producer proves settlement; slot absence alone grants no retry. At most one authorization is current. A previous authorization is superseded only with fresh proof that it never released input and can no longer do so; append its revoked disposition instead of changing its history. This allows repeated pre-input process loss without granting concurrent capabilities or allocating a second body reservation. A stale capability validates both the current edge and current lease at the trusted writer and refuses. The new capability carries the original reservation identity and the successor edge; productive observers validate both inside their ordinary charging transaction. Saved edge/proof references alone cannot construct it. No caller can bypass this constructor using the ordinary first-body factory, which still refuses an existing reservation.

The trusted input writer durably records the exact prompt digest and release-attempt marker, bound to that authorization/native invocation, **before** any body bytes can escape. A crash after this marker is exposure-uncertain even if the transcript is empty; it cannot enter unexposed recovery. Recovery then reconnects the original invocation or follows proven conversation/outcome recovery. A positive native release receipt proves exposure; absence of that receipt does not prove nonrelease. A crash before the marker can return through the nonrelease producer only after old writers/resources are conclusively fenced. This conservative interval is required because a durable database transaction and transport delivery are not atomic.

Recovery allocates no second body reservation and never refunds or resets prior admissions. Reconciliation and proof-only settlement are unpaid. Actual new model/resource admission through the successor obeys current budgets and records the original reservation plus successor attempt; any admission already charged before a proven nonrelease remains charged. A release retry cannot reuse an old charge as a fresh budget grant. Confirmed merge allowance remains unchanged by every such transition. Capacity or proof failure retains the request and a specific blocker rather than manufacturing nonrelease or completion.

### 5.2 Exposed invocation and outcomes

Recovery first inspects or reconnects the **same actual retained invocation**. It may observe/finish already-admitted work or request checked quiescence; it cannot restart a command from a serialized plan. Continuing a retained process after a fence requires the actual retained native/resource transfer proof and current execution authorization. Dropping handles, timeout, source hashes and an empty process listing are insufficient.

For a certain completed native outcome, recovery acquires fresh original `NativeCompletionProof` and records the observed outcome. Persist a private response journal bound to the original dispatch/launch/completion reference before applying the message and queueing its reply. This permits exact replay after database acknowledgement loss. If the application died before journaling, recover the actual response from the authenticated retained native result/export; do not fabricate a reply or call a model to recreate the old answer. If that result is unavailable, record the missing-result blocker, not completion.

The version-1 response journal is an immutable UTF-8 payload plus a strict envelope. The payload is at most 1 MiB of exact decoded response bytes, stored as `owner-response-DISPATCH_SEQUENCE-LAUNCH_SHA256-RESPONSE_SHA256.utf8`. The envelope is at most 32 KiB and contains version, workflow/request, original dispatch sequence, optional completing continuation sequence, completing native launch/reference and observation digest, original store/native-owner references, measured binding, payload basename/length/SHA-256 and UTC time. Full native evidence stays in its existing bounded native history, not an unbounded embedded object. The envelope and payload are private current-user regular single-link files, no-clobber/fsynced and read nonblocking with exact bounds; unsupported schemas or conflicting bytes refuse.

Failure to admit or persist this journal, or an authenticated response exceeding its representation bound, records `owner-result-storage-blocked` with the actual retained native-result/hold reference. Do not truncate, generate a replacement answer, apply the message or repeat the coding body. Record the proven native outcome as observed-but-not-settled, preserve its upstream result under the original storage hold and let unpaid result reconciliation retry admission. P5 must provide retention and admission for these upstream results as well as journal payload/envelope before productive ingress; if a supported larger/chunked representation is needed it requires an explicit versioned schema, not a silent limit override. This is unavailable durable workflow evidence, not a failed notification send: once completion/reply intent is durably settled, Discord delivery failures never undo execution or determine workflow success. Native/result evidence that is itself unprovable remains an outcome-uncertain hold instead of a fabricated result reference.

If work was interrupted after body exposure, automatic recovery never resends the original body. It can issue a **new, explicitly recorded continuation** only when a native producer proves that the original actual provider conversation is restorable and the original resources are quiescent/transferred. The continuation prompt asks the existing session to continue from recorded state under current accepted requirements/paths; it does not substitute a fresh session or repeat the original instruction. It is a real bounded model admission, not unpaid reconciliation. Bind it to the original request/body/preparation, actual conversation frontier, current authorization/generation and prior dispatch. CAS consumes that frontier so two controllers cannot issue the same continuation. Another uncertain outcome without a new proven frontier cannot be retried by TTL.

The frontier is a semantic native checkpoint: original store binding, actual provider/conversation identity, the latest committed provider turn/message identifier, canonical digest of its validated transcript prefix, and the controller input-release receipt to which that provider progress responds. It excludes ownership generation, audit heartbeats, wall clock, temporary files and filesystem timestamps. Ownership transfer alone cannot create another frontier. The producer must validate the provider/version's actual retained format and append/compaction ancestry; a changed file hash or a claimed session string alone is not progress. Unsupported or unprovable compaction holds. A continuation needs new proven provider progress since the last consumed frontier, or a distinct trusted known-unstarted/nonproductive outcome for that attempt plus its normal readiness/cooldown transition. Merely appending another controller prompt or reaching retry time does not qualify. Unknown transport/outcome remains uncertain.

Completion after a continuation records both original dispatch and completing continuation/native generation. It applies exactly the original captured request, preserves later queued messages and invalidates current approval/evidence for revalidation. It does not assert that all current workspace edits were authored by that body. Current head/data/provenance still need normal verification and independent review.

If actual conversation identity/restorability or native outcome cannot be proved, keep the original request/outcome uncertain and block automatic coding. The owner can use the separately authenticated T/D recovery/provider-switch/correction flow to authorize a new instruction/context with retained history; the system must not silently replay the old request or erase previous/unknown authors. These rare explicit resolutions are not the routine restart path. Mid-body restart tests for both real-format Codex and Claude fixtures must establish the routine path before productive ingress.

## 6. Settlement matrix

Publication activation establishes accepted criteria, not owner-input completion. Recovery rolls the exact accepted metadata forward when its original bytes and authority survive; a newer pause/message is not permission to discard those criteria.

| Observed state | Settlement and next authority |
| --- | --- |
| Intent/activation durable; original native handoff pending | Reconcile that exact native intent under metadata authority. Preserve unknown effects and input; no replacement origin/UUID. |
| Exact old or next canonical state; original prepared bytes available; same candidate | Finish native/scope/metadata publication under original proof. Preserve current controls; expose no productive guard from metadata settlement. |
| Original preparation missing; bound next prepared evidence and original input/candidate data survive | Reconstruct only the exact original version-2 bytes and require the original artifact digest. Restore no-clobber under recovery authority; conflicting bytes refuse. This is exact-byte recovery, not a new proposal or a new context. |
| Candidate head changed, physical candidate unchanged | Metadata may settle without discarding edits. Execution requires fresh head/provenance/acceptance verification and current authorization; no old-head receipt survives. |
| Physical candidate missing/replaced or scope cannot be proved | Record a candidate/scope-unbound disposition and retain pending intent plus all actual effects; this is not publication completion and does not authorize a new manifest write. An already-written exact next manifest remains uncompleted. Do not bind policy to a substitute or rebuild unknown uncommitted data from remote. Restore/prove the original candidate/scope or use supported explicit adoption/correction with its own native/data authority before ready completion. |
| Prepared evidence unavailable or canonical state is neither exact old nor next | Retain all bytes/activation/native/scope effects and record a specific evidence-unavailable hold. Do not roll back accepted criteria, regenerate a completed context, overwrite a third manifest or treat an absent pending pointer as ready. Restore exact retained evidence or use P4's separately authorized correction context. |
| Explicit pause or another security/owner hold arrived | Settle provable metadata/outcomes while preserving the exact newer hold and checkpoint. Productive continuation waits for its independent current authorization. |
| Later ordinary owner messages arrived | Preserve them as separate pending requests. They are not implicitly applied by the older completion; normal serialized processing prevents merge while input remains. Explicit control commands retain their stronger fencing semantics. |
| Body completed before/after a control or terminal transition | Record actual proven outcome/private reply without changing the newer hold/terminal state. Never convert that into approval, a second shipment or post-terminal work. |
| Original native authority or cleanup is unprovable | Quarantine with the exact missing-evidence action; retain resource/storage holds. Restore original authority through supported managed recovery. No fresh epoch, timeout-based cleanup or fabricated empty inventory. |

Completion/disposition is append-only and validates actual native/scope/canonical facts. Ready completion, blocked observations and terminal settlement are distinct records. Ready completion removes the pending pointer atomically with its completion/event. A blocked observation retains the pointer, releases only its metadata worker lease, and records a specific retry/action; later recovery appends new facts rather than editing the old observation. Terminal settlement may remove the pointer only with an actual terminal-native checkpoint and checked native effects; it performs no new publication without the required scope proof, grants no productive authority and preserves terminal state. Default productive admission checks the latest activation's ready completion and canonical lineage, not pointer absence. A blocked workflow has an owned restoration/correction path and diagnostic access while unrelated workflows continue; unavailable evidence never justifies weakening its productive gate. Generic resume or budget reset cannot convert blocked observation into ready completion.

Unavailable original authority is a truthful exceptional hold, not a promise of automatic success. Reconciliation is bounded, unpaid and fingerprinted by actual intent/native/resource/candidate/policy evidence. Unchanged quarantined evidence gets cheap observation/backoff and a durable private blocker, not repeated builds/model calls. Other ready workflows continue. Required capacity is reported without lowering storage/resource floors.

## 7. Test-first exits and carrying costs

No intent writer is introduced until the native/scope producers, productive/metadata separation and complete reader/writer inventory satisfy their contracts. Record real red assertions against the parent before implementation; use production entry points with temporary repos, isolated owned stores and fake clocks.

1. Reproduce stale cached/ordinary acquisition replacing accepted criteria; cover ordinary amendments descending from owner acceptance. Every canonical reader, orphan writer, scope writer and cached callback must be enumerated and fenced structurally.
2. Implement/prove the borrowed native/scope/input/outcome capabilities. Test loss/replacement of original store, policy, session, runtime/resource identity, scope and candidate; descriptor/child survival; and unknown setup/cleanup. Saved projection data must fail to mint capabilities.
3. Atomically join intent/activation/fence. Crash after staged evidence, before/after activation acknowledgement, and lose/change each row/event/projection independently and in legacy-shaped pairs. No new generation/proposal/charge on exact replay.
4. Fault every native handoff, scope, evidence/history, canonical rename, completion and pending removal boundary. Exercise old loaded guards and competing owner controls during each boundary. Use subprocess death and actual failed-persistence cases, not only constructed final files.
5. Recover using a new metadata generation and original immutable lineage. Cover pause, resume, new input, cancellation, external merge/retirement, head edits, candidate replacement, missing exact bytes and third canonical state. Assert original data/controls/accounting and native effects remain intact.
6. Kill the process before/after reservation acknowledgement, successor CAS, release marker and actual input write; prove the original reservation remains unique, stale capabilities cannot write, uncertain release never becomes nonrelease, repeated proven-unexposed recovery preserves lineage/charges, and an initial unexposed bridge requires no fabricated conversation frontier. Prove no body replay after exposure; reconnect original invocation, recover exact completed output, and resume a proven original interrupted conversation under both provider fixtures. Duplicate continuation/frontier and fake session-ID cases must remain blocked with unchanged counts. Unavailable requested providers never fall back silently.
7. Add current-source/full-cleanup, P3 public projection, P4 correction and P5 storage admission, then connect CLI/Discord worker ingress. Normal updater rollout and all #1715 live/fault/soak/five-shipment requirements remain necessary. A live merge by an older build is partial evidence, not completion of this protocol.

Carrying costs are explicit: new bounded journal/lineage schemas and strict validation; all-caller productive admission and canonical ancestry; native prepared-invocation/outcome proofs; original response retention; and P5 reservation of original preparation, staged evidence, journal, responses and rollback/recovery references. No automatic deletion or migration of incompatible history is permitted to make the feature run. Backups remain managed deploy snapshots. Existing historical inspection remains available without productive authority.

## 9. Native input-release component limits

The component requires the protected original logger/store/runtime authority, exact prepared-launch reference and the exact resource-binding receipt. It rejects a second input attempt on the same live `Launch`, even after an unsuccessful attempt; a persisted marker is not replay authority. Prompt contents stay out of audit records. The protected append and current workflow checks finish before stdin release. A failure after the append retains the marker and sends no input through this path; a process death in that interval retains exposure uncertainty even when the fixture recipient proves it received no bytes. No general recovery authority is inferred from that fixture observation.

This closes the missing durable marker at the two existing writers. The proposed body input-boundary contract is larger. Section 11 now implements the normal original body/model/launch/resource/prompt join. Durable successor release authorization, actual retained writer/resource exclusion, positive delivery receipts, native nonrelease and restorable-conversation proofs are still unimplemented. The in-memory once-per-launch flag is not a durable request-wide deduplication mechanism. No metadata intent writer, automatic request replay, owner worker ingress or productive public-output permission is enabled by this component.

Component commands, red/green evidence and limits are recorded in [the input-release proof](1703-native-input-release-proof.json). This receipt does not complete P1/P2 or #1715.

## 10. Once-only body model admission

A once-only outer body reservation did not by itself prevent the reasoner's internal retry from admitting another native model call. The component fix joins the original live reservation and preparation to the existing `native_model_admitted` event and resource charge. Its version-1 `owner_body` payload binds the original request, reservation sequence/digest and exact preparation. `workflow_owner_body_model_admission` is a unique-per-request projection of that same event, with its charge receipt and event sequence; it is not an independent verdict or permission store. Projection, event, charge, bounded attempt and cumulative accounting commit in one immediate transaction. Each record is bounded to 16 KiB and history to 4,096 entries, retaining the original evidence rather than resetting it.
