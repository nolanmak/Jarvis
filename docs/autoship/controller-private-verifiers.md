# Controller-private behavioral verifier sources

Status: implementation design under audit; not deployed and no shipping authority.
Owner: acceptance controller (#1709) with C/#1710 providing source freshness; #1703 acceptance remains unchanged.

## Problem and verified boundaries

Current `prepare_acceptance_for` installs independently registered adapters into the candidate, and amendment activation commits replacements there. `execute_registered` exports literal Git blobs and overlays pinned files read from that candidate. PR #1870 now forbids those dedicated adapters in product Git trees. The actual #1669 private candidate 4c1d6f fails the new CI test for `crates/augmentagent-messages/src/bin/autoship_case.rs`. Removing the guard or skipping its check would preserve the wrong product behavior.

`PreparedAcceptance` already durably stores the exact proposal files outside worker write roots. `RegisteredContract` already hashes those files into its contract hash. Use those authorities together; neither the worker checkout nor an artifact cache becomes a source authority. Required GitHub CI remains the product merge signal. The isolated behavioral oracle remains an additional acceptance requirement, not a local duplicate of all required CI.

## Decisions and reasons

D1. The product candidate is a clean committed Git tree without dedicated acceptance files. Its Git HEAD is the only product head claimed by review, hosted CI, acceptance bindings and merge. The private execution tree is that literal committed tree plus exactly the registered adapter map. Its overlay does not change the product head. This makes publication exclusion structural instead of relying on a reviewer to delete tests.

D2. Add registration APIs that register and verify pinned bytes from an in-memory `BTreeMap<String,String>` validated by the existing strict proposal parser. The keys must equal the union of all pinned files, not a superset/subset. Hash UTF-8 bytes exactly; verify contract metadata and recompute the existing contract hash. Preserve the serialized registration shape, source identity, original baseline, criterion strings, oracle values and command restrictions. `verify_integrity(root)` remains useful for the private execution tree; it must not be replaced with metadata-only checking where bytes are executed. No arbitrary directory walk or candidate-authored map is permitted.

D3. Pass the registered adapter map explicitly through baseline execution, candidate execution and materialization. Before any subprocess, verify the map against the registration and ensure each adapter path is absent from the literal product Git tree. Export product source with the existing literal-blob exporter, install adapters with exclusive creation, verify the resulting private tree using `registration.verify_integrity`, then execute using that tree. Reject symlinks, nonregular parents, path traversal and collisions. Execution must retain the existing `isolated_observation` kernel confinement: the private execution source is read-only through `codex-command-sandbox.py` Landlock rules, with write access only to the disjoint runtime and registered target. Canonicalize all three and refuse overlap in either direction; include all descendants in that confinement. Never grant the source as a write root or substitute chmod/endpoint hashing for this control. Add an actual child test that attempts adapter rewrite-and-restore and an alias/overlapping-write-root test; both must be refused before altered bytes execute. Missing confinement is an infrastructure hold, not an unsandboxed fallback. The sandbox setup outcome must reach the controller as a trusted typed setup failure separate from the candidate exit code; do not classify exit 126 or candidate-printed diagnostic text alone as that authority. Update `isolated_observation`/its supervisor result handoff and callers so a genuine setup refusal never becomes `UnexpectedFailure`, intended red or a product-repair model call. Add an actual enforced-setup-failure round-trip test with unchanged paid accounting and a candidate exit-126 control that cannot forge that setup disposition. Verify private adapter integrity before and after each observation; `observe` checks this actual private tree. Recheck product HEAD and clean state before accepting results. Ignored/staged/untracked candidate files never supply bytes. Replacing a registered map, mutating private adapters, changing product HEAD or losing cleanup evidence cannot produce a receipt.

D4. Baseline registration uses the same composition at the unchanged original baseline, without installing adapters into its Git worktree. A path already tracked at that baseline is a collision, not permission to overwrite or delete it. Initial scoping or the existing bounded independent correction must choose an unoccupied dedicated adapter path. Collision failure is not an intended assertion red. Introduce a typed pre-execution `VerifierSourceCollision` carrying only bounded literal colliding paths and their immutable Git source binding. In initial `prepare_acceptance_for`, route this error alongside inadequate initial verifier output to the existing bounded independent correction authority; do not rely on `BaselineNotRed`, which currently does not catch installation errors. The controller persists the collision fingerprint with the original proposal/source/base and reuses only a completed correction whose full requirements and vacant adapter paths validate. This is definition correction, not product-code repair: no repair-model dispatch, baseline red or ship credit. Repeating the same collision must reuse its recorded result/hold and existing correction budget, never reset the family or obtain an unbounded fresh call. In amendment preparation, the same typed error permits only the existing bounded independent amendment-correction path before pending activation, preserving original criteria and approval/round accounting; exhausting that path gives a durable verifier-definition hold until actual inputs or explicit owner controls change. Test both initial and amendment collisions through the real callers, including crash/replay and zero extra calls on unchanged input. Existing historical files are never removed from the original baseline. Independent baseline red still requires the controller oracle to observe the intended mismatch under the current environment.

D5. New candidates never install adapters. Amendment preparation independently verifies/reproduces the replacement proposal as before. Activation persists a new protected proposal/registration and existing workflow manifest, with existing authority, criterion, source, scope and environment checks. It changes no product files and creates no harness commit. Advance the manifest before deleting the pending record; retain immutable prior history. A crash resumes the same approved transaction. Activation alone provides no candidate green: verification, alignment, review, current GitHub checks and merge checks must all bind the current product head and new contract before merge. Source scope registration keeps adapter paths protected, even when absent; model edits cannot introduce them.

D6. Normalize installed legacy adapters before activating a new byte-map-only amendment. If a version-1 pending file amendment already exists, first finish its recovery transaction under the strengthened checks below without treating its historical receipts as current shipping proof, then normalize its installed result. The current `resume_pending` is not sufficient unchanged: its `already_active` branch skips diff checking and `commit_candidate_named` stages `-A`. Replace that behavior with exact-path staging and unconditional product-tree/index/untracked checks at every replay, including already-active manifests. Derive the expected file-only result from `pending.original_head` and the independently approved old/new adapter maps. Before creating any commit, durably record its exact tree, parent, transaction identity and deterministic commit metadata/OID; replay may only adopt that exact commit. Existing already-committed version-1 states need original protected controller audit evidence tying the exact commit/tree/parent to that pending transaction; tree equality or a commit subject alone cannot supply it. If that historical proof is absent, retain a typed legacy-recovery hold rather than invent a successful commit or stage unrelated changes. This historical unknown-state recovery is tracked as O2; it blocks that affected workflow, not clean new transactions. The removal registration must be the protected current or immutable completed historical registration that exactly matches the installed adapter inventory and source/workflow; retain its bytes and bound history in the removal intent. A historical match is only removal authority, never current verification authority. Mixed old/new installations with no completed matching inventory remain held for their original pending recovery; never guess which bytes to delete. New amendments cannot strand old adapters by discarding this inventory. Test both changed-path and changed-byte replacements.

Legacy candidates such as #1669 require a controller-owned, restartable removal transaction, never operator deletion or history rewriting. Admission requires a quiescent owned workflow; exact original/source/contract/head binding; clean index/worktree; complete registered map integrity; and every proposed removal satisfying the reserved harness predicate, byte equality to that registration, absence from the original baseline and current upstream contribution base. Refuse any mismatch, upstream collision or uncertainty without deleting anything. Only named registered paths may be removed. Stage those exact paths and make a normal successor commit with existing controller Git helpers; never stage unrelated changes or change product implementation. Persist a private removal intent before touching the candidate, including original tree/head, path hashes, expected resulting tree, installed and active contract/source/workflow identities, exact contribution-base B, exact admitted origin/main U and transaction version. Revalidate U and ownership immediately before the first deletion; if U changed, refuse with the worktree untouched and re-admit against the new upstream. After the first deletion, finish only the intent bound to U: upstream advancing does not reinterpret or expand its deletion authority. Finish that bounded transaction, then let the existing upstream reconciler integrate/re-scope the new main before any fresh acceptance/review/merge. A collision introduced upstream is a normal explicit reconcile hold, never permission to delete upstream product source. Test upstream changes both before first deletion (zero edits) and after it (exact bound recovery, no stale-head merge authority). Recovery accepts only that exact original head with an allowed removal prefix, or the expected successor tree with its exact parent and controller transaction identity. Preserve unresolved state; never infer ownership from a filename or adopt a matching arbitrary commit. Persist completion and new head before clearing intent. Existing owner/lease controls fence the transaction. The normal pipeline later pushes the new head and reacquires independent review, hosted CI and acceptance; all old head-bound receipts and pending reservations remain ineligible. Model calls, allowance, original baseline and criteria are unchanged. Outstanding dispatched/unknown remote merge operations must first reconcile through existing merge evidence rules; removal cannot race or erase them.

D7. Private adapter bytes are compiler inputs, not an exemption from source freshness. C/#1710 must bind the full product-plus-adapter composition, contract hash, source generation, toolchain/runtime and observed inputs through its single final proof API. Reconstruction, including identical HEAD or changed adapter bytes, starts a new generation under #1807 D1–D8. Within-generation compatible reuse and trusted dependency reuse remain required. Do not mint a parallel freshness flag or treat registration hashes as proof of compiled freshness. Existing metadata, mtime and successful exit are insufficient. Old receipt formats remain readable for history but cannot authorize new verification/merge after cutover. The current #1811 draft has no final accepted C schema/API: consuming that final API and its old-writer/reservation cutover is an explicit implementation-acceptance blocker, not an implicit guarantee from this design.

D8. Storage is the existing private source allocation and registered verifier target with current admission, resource policy, ownership and cleanup holds. The current behavioral executor does not yet create the durable storage hold used by `self_improve_ci_vm`; `record_outcome` alone is not the stronger `verified_quiescence` proof. Implement that join explicitly: before spawning, create the existing `ci_holds::Hold` bound to exact source, registered target and runtime/supervisor; use the existing storage-aware descriptor inheritance and `admit_with_observer` pattern to bind the exact typed resource command before releasing execution. Require the same command identity, original admission/completion evidence and kernel-verified quiescence, then settle its hold before returning an accepted observation/receipt. Hold creation/admission failure cannot run unbound code or emit a receipt. Cancellation, crash, output/space failure and unknown cleanup retain source, target and original supervisor evidence; existing storage reconciliation owns their later verified retirement. Test actual descendant survival, cancellation before/after admission, controller crash, failed admission and repeated recovery through the real verifier caller, asserting no source deletion/prune eligibility or receipt before verified cleanup. Dropping a Rust handle alone does not prove teardown. Unknown cleanup retains both sources and managed storage; existing reconciliation owns eventual retirement. Protected proposal bytes remain under existing acceptance-store retention so pending verification can reconstruct them. Do not add host caches, raw database backups, a new credential/network grant or a second cache-generation authority.

## Interfaces and callers

The implementation may name helpers differently, but must expose these semantic operations:

- `register_from_files(contract, baseline, environment, pinned_map)` and transition equivalent: validate exact map and metadata and return the existing registration format.
- `verify_registered_files(registration, pinned_map)`: validate exact names/content and registration hash without worker filesystem access.
- `materialize(product_root, product_head, registration, pinned_map, target)`: return the existing owned private execution tree after composition and integrity checks.
- `execute_registered(product_root, registration, pinned_map, audit)`: execute only that materialization; observe against private-tree bytes while binding receipts to the original product head.
- `assert_verifier_receipt_current`: verify protected proposal/registration identity and current product head/environment, clean product tree and no dedicated adapters, then consume the current C proof and original receipt; never require adapter files in the product checkout.

Update initial prepare/register/reproduce, environment amendments, pending amendment recovery, legacy migration, candidate verification, receipt-current checks, review/alignment evidence and diagnostic fixtures together. Audit all direct `verify_integrity`, `observe`, `execute_registered`, harness-install and adapter-read callsites. Provider evidence presents independently pinned adapter bytes from the protected proposal, separately from product Git source, without changing the provider request cap or call budgets. Genuine requirement/product source remains committed-source-only. No builder output selects a replacement proposal.

## Non-goals, risks and open threads

No CI guard exceptions; no GitHub required-check bypass; no original-baseline rewriting; no weaker oracle; no resetting model or ship counters; no manual merge counted as auto-ship; no benchmark. This design does not implement native owner transfer or Discord session continuation; those remain #1758/#1713 work and retain their own acceptance blockers.

Accepted carrying cost: source reconstruction may recompile workspace artifacts. C must still prove compatible within-generation reuse and later trusted external dependency reuse. Private adapter retention uses existing protected acceptance history, not a new mutable source store. Legacy collisions intentionally hold; independent bounded correction is the recovery path, with no automatic deletion at the original baseline.

Load-bearing open thread O1: C/#1710 owns the final single source-generation/freshness proof API, scope and writer/reservation cutover. #1811 currently remains draft and explicitly lacks full input closure and shipping authority. Trigger: its audited API and real guest acceptance become available. Blocks step 5 and live activation; source composition tests and steps 1–4 can proceed without claiming fresh compiled acceptance.

Open thread O2: the acceptance-controller owner must define authenticated recovery for a historical version-1 pending transaction whose prior commit cannot be bound to original controller evidence. Trigger: the migration census encounters such a state. Carrying cost: retain original pending/history/head and owner controls; no file edits or new receipt authority. Blocks migration/live acceptance for that affected workflow until the supported recovery is implemented and tested. Do not silently use `already_active` or create a new productive origin to escape it.

Audit status: fresh-reader and conversation review plus all 17 canonical seams (covering all 65 original mapped occurrences and three added amendment boundaries) checked. Findings resolved in the text: installed-registration ordering, read-only execution, upstream pinning, legacy replay exact-head/staging, collision correction ingress, trusted sandbox setup failure classification, new-versus-legacy commit semantics, and durable resource-to-storage cleanup proof. O1 and O2 remain explicit acceptance blockers; no final handoff-readiness, implementation completion or live-shipping claim. Implementation tests must establish these new joins; the audit is not execution evidence.

## Glossary

Product tree/head: exact committed source that will be published and merged. Private execution tree: literal product source plus independently registered adapters, never published. Registration: existing immutable contract plus pinned-file hashes and baseline/environment binding. Source generation/freshness proof: C-owned execution/cache identity and compiled-input evidence; registration is not a substitute. Legacy removal: controller transaction changing only previously registered candidate adapters via a normal successor product commit, not alteration of historical baseline. Authority approval: permission to test a proposed amendment, not evidence that the baseline is red or candidate green.
