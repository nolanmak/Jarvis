# Owner acceptance publication and recovery

Owner: D/#1713 and T/#1712, using the existing workflow, native ownership and private verifier services. This is an implementation checkpoint, not a completed handoff or permission to enable productive owner coding. Epic #1703, private-verifier D1–D8 and original owner holds remain binding.

## Decisions

1. An independently prepared acceptance artifact must be durable before workflow activation. Its private `Stored` record contains the complete original owner input context, proposal, protected adapter map, registered contract and actual intended-red baseline receipts. The existing input-context hash selects `owner-preparations/<context_sha256>.json`. There is exactly one immutable completed artifact per context: creation uses `persist_noclobber` and directory fsync; an existing artifact is reused only after exact input and protected registration validation. A conflicting write refuses and retains the old bytes, including on concurrent acknowledgement loss. Once a completed artifact is durable, no retry regenerates or overwrites it. Before that boundary, the producer reuses the existing `scope_authority::persistent_revision` completed-response journal; baseline reproduction and unpersisted provider responses may repeat only under the existing workflow/native admission, actual call accounting and bounded budgets. This is not an exactly-once inference claim. Concurrent producers cannot overwrite a winner: a no-clobber loser returns failure and a subsequent retry reopens the saved winner. A lost/uncertain native outcome still requires original native reconciliation before further dispatch; an absent artifact is not quiescence evidence. These read-only preparation retries never authorize repeating an exposed owner coding body. An independently authorized definition correction needs a distinct versioned context/transaction; that owner-correction join remains blocked work below. The producer returns the exact private file's identity, not only an in-memory proposal. This prevents a later recovery from guessing which proposal was activated.

2. Every new private activation carries a version-1 preparation binding with exactly `version`, `artifact_sha256`, `context_sha256`, `registration_sha256` and `baseline_receipts_sha256`. The artifact is at most 4 MiB, a current-user-owned regular single-link file with no group/world permission bits (created as 0600), opened with `O_NOFOLLOW|O_NONBLOCK`; its bytes must equal `serde_json::to_vec(Stored)` after parsing. `artifact_sha256` hashes those exact bytes. `context_sha256` uses the existing `Input::key` (`SHA256(serde_json::to_vec(Input))`). The registration and complete receipt vector hashes use `native_vm::ownership::canonical_bytes(serde_json::to_value(value))`, the same canonical encoding as existing ownership and baseline history. Vector order is retained. Every digest is lowercase 64-character SHA-256. Unknown fields and unsupported versions refuse. The registered metadata already binds adapter paths and content hashes; its existing `verify_files` still checks the actual protected byte map. These digests are binding data, not independent activation, cleanup or shipping authority. The guard still authenticates the current owner request, candidate, pause revision, source, previous contract, native store and generation.

3. Private activation writes its preparation binding and complete baseline receipts to `workflow_owner_preparation(request_id PRIMARY KEY REFERENCES workflow_owner_revision(request_id), record TEXT NOT NULL, receipts TEXT NOT NULL)` in the same SQLite transaction as the existing activation, checkpoint, review invalidation and generation fence. `record` is the binding above (maximum 4096 bytes); `receipts` is the complete `VerifierReceipt` vector (maximum 4 MiB). The existing `owner_acceptance_registered` or `owner_contract_revised` event carries the identical binding in optional `preparation`; its existing event limit remains 32 KiB. History validation uses parsed-value/reserialized-value equality as well as strict schemas, joins both directions, verifies the registration digest and intended-red baseline, and rejects one-sided missing, changed or orphaned projections. A missing pair remains unproven legacy-shaped inspection metadata under Decision 4. Preparation data counts toward the existing 128 MiB / 1024-activation history bounds. Initial and revised private acceptance both retain their full baseline receipts. Acknowledgement loss must not create another activation or replenish any budget.

4. Replay compares the exact preparation binding and baseline, in addition to the existing original request, body digest, previous/next contracts and binding. Reopening the database changes none of these identities. Old activation events without preparation bindings remain historical metadata; no binding or private file may be synthesized for them. There is no timestamp/version cutoff that grants missing preparations legacy execution authority: every activation without its original preparation is unproven for productive owner admission, including a new activation damaged to look legacy by removing both event preparation and its projection. Read-only history inspection can retain that legacy-shaped metadata; this is explicitly not proof that all new-history damage is distinguishable from legacy records. Both first-builder and continuation paths now require the original producer's opaque preparation through Decision 8. `has_owner_acceptance_for_turn` checks intact private preparation history, rather than revision existence; this boolean is inspection data, not the productive capability. P1 must still add completed-publication admission before enabling the consumer. Reopening the database cannot upgrade missing preparation metadata. A contract hash alone is insufficient.

5. The staged publication intent now binds this receipt to the saved prior canonical manifest and exact next manifest/evidence file; the activation transaction records that immutable intent and its pending pointer with activation/fencing. This is pending metadata, not completed publication. The owner publication writer, metadata recovery authority and shared completed-publication admission predicate remain implementation work before enabling the consumer. Publication occurs only after the original-store native handoff and registered write-scope update succeed. Every ordinary manifest consumer must hold while an unresolved publication intent exists. Replay must check the original artifact bytes/context, activation history, current owner intent, unchanged candidate and complete previous-or-next manifest before any write. Immutable evidence/history, manifest replacement, completion persistence and pending deletion need fault tests at every acknowledgement boundary. The existing canonical namespace and manifest remain the only acceptance source; this adds no alternate verifier engine or verdict store.

6. A claimed owner turn does not become replayable because its process disappeared or lease expired. Recovery after process loss needs authenticated original native closure and a guarded ownership transfer before it can finish publication. The current claim API intentionally refuses claimed/uncertain turns; publication recovery must not bypass that rule, clear a pause, replay an exposed body, invent a conversation, or reuse an old generation. D/R own that recovery join before productive worker ingress is enabled.

7. Newly saved preparation envelopes use `Stored { version: 3, input, candidate, canonical, prepared }`. `Input` and its version-1 context key remain unchanged. Physical candidate identity is deliberately outside that key: replacing a checkout must find and refuse the original context artifact, rather than select a new filename and regenerate acceptance for the same request. The envelope and every nested candidate record reject unknown fields. A cached artifact without the version-3 envelope or original candidate/canonical identity refuses in place; the producer never fills in identity, overwrites the file or falls through to a paid preparation. Recovery of older/unversioned envelopes needs an independently authorized migration/rebinding protocol before productive recovery; no automatic compatibility path is claimed.

   `canonical` has strict version 1, canonical absolute `control`, the exact `source`, and `manifest` containing the original manifest's exact UTF-8 bytes or null for proven absence. Manifest bytes are bounded to 4096. Original orphan baselines are recovered or refused before independent preparation; a manifest discovered during retry is not treated as absence. The input-context key is unchanged, so version-2/missing-canonical artifacts remain at their original key and refuse without regeneration. This snapshot is preparation input, not canonical publication or dispatch authority.

   `candidate` has exactly `version: 1`, `root`, `git_pointer`, `git_directory`, `common_pointer` and `common_directory`. Each directory contains canonical absolute `path`, filesystem `device`, `inode` and `uid`. Each nullable pointer contains its absolute `path`, `device`, `inode`, `uid` and lowercase SHA-256 of its exact bytes. The root, actual Git administration directory and actual common directory must be owned directories; symlink leaves refuse. For linked worktrees the `.git` file and optional `commondir` file are opened with `O_NOFOLLOW|O_NONBLOCK`; each must be current-user-owned, regular, single-link and at most 4096 bytes. Pointer bytes must be UTF-8. Zero or more terminal LF bytes are removed for target parsing only; no other whitespace is trimmed. The remaining Git pointer must begin with exact `gitdir: ` and have a nonempty target; a common-directory pointer is the nonempty path itself. Any remaining NUL, LF or CR refuses, including CRLF framing. Repeated terminal LFs are allowed framing, remain in the hashed original bytes and therefore cannot be added to an existing saved pointer identity. Relative targets resolve against their containing directory. Captures recheck directory identities and pointer bytes after traversal. Ordinary product edits do not change this identity; Git metadata copying/replacement, aliases to a different physical checkout and changed pointer bytes do.

   The producer captures identity before independent preparation and rechecks it on cached reload, before saving and before activation. The owning guard rechecks the exact artifact after asynchronous inspection, across native settlement and around write-scope registration. The artifact digest already retained by the activation transaction consequently binds this candidate data too. This is point-in-time physical binding data, not repository/workspace authorization, original native closure, a held directory capability or source-content/freshness evidence. P1/P2 still require authenticated provenance and original locked native/storage proof across their actual mutation boundaries. A replacement checkout cannot be authorized merely by recomputing this record or by restoring the same commit at the same path. Recovery must locate the original saved input-context key through immutable lineage; deriving a fresh key from a later recovery lease would incorrectly evade the original artifact. Device/inode snapshots do not solve inode reuse after deletion; original locked native/storage and workspace provenance remain independent requirements.


8. Productive owner-body APIs take the original `Arc<PreparedOwnerAcceptance>`, not a reconstructed `PreparedAcceptance`. The producer rechecks its exact private artifact, physical candidate, original request/body/owner/pause/source/head and the single guarded activation generation (`original + 1`); the current store must retain the identical preparation binding for that turn. This generation rule deliberately does not authorize process-loss recovery: P2 must supply immutable original-input lineage before any later recovery generation can pass. Both first-builder and continuation reservations require the binding in their SQLite transaction. First-builder reservation additionally retains the existing original locked `UnusedNativeOwnerProof` and all baseline/cleanliness/attribution checks. The old preparation-free continuation reservation is compiled only for metadata fixtures; the preparation-free first-builder wrapper is removed.

   The existing version-1 owner-body `Record` gains optional `preparation: OwnerPreparationBinding` for historical parsing; every new production reservation writes `Some(original_binding)` into both the dispatch row and its identical `owner_body_dispatch_started` event. History with a preparation must still join to its intact original activation/projection and baseline. A missing field on old history is descriptive only. A saved row cannot reconstruct `OwnerBodyDispatch`, whose constructor remains the once-only factory. The proposed P2 protocol preserves this rule: a reserved-but-proven-unreleased request requires a different borrowed recovered-release capability and immutable successor edge, retaining its one original reservation. That constructor, native nonrelease/input-writer proof and lineage-aware readers are not implemented by this checkpoint; a saved row or empty transcript grants no exception. The live non-cloneable dispatch instance is shared by reference with the original opaque preparation in `OwnerBodyAdmission`; shared references do not create another reservation or permit replaying the prompt.

   After reservation and before calling a provider, the guard narrows its dispatch and model-accounting observers to that captured admission. The callbacks retain it across thread hops and after body success/failure; absence of task-local context never restores ordinary admission. Dispatch revalidates the artifact and exact persisted reservation. Model admission also checks the actual native provider and builder attribution, then validates current lease/turn/pause, original preparation and captured reservation in the same immediate SQLite transaction as existing model attribution, bounded budgets and resource charging. Even if both the saved dispatch and its event lose the new field and look legacy-shaped, they differ from the captured original reservation and fail. Refused artifact/activation/provider/turn checks and failed audit persistence leave model and bounded-attempt charging unchanged. Original owner pause, pending input and merge accounting remain unchanged. Completion still requires the fresh original native completion capability; a reserved/charged model or reply is not completion, publication, owner resume or shipping authority.

   This supplies original-preparation/body admission, not P1's canonical publication gate, native source execution proof or P2 recovery. Metadata fixtures and observer calls do not prove live provider/VM execution. Productive worker ingress remains disabled until those separate requirements and public-output protection are connected and verified.


9. Publication/recovery must distinguish an explicit owner pause from the temporary input barrier. `OwnerControl.paused` denotes the explicit hold; the barrier is derived from the existing pending owner-message records, not a new independently mutable flag. Enqueue persists the input before acknowledgement, preserves the existing explicit pause value, and advances the intent revision unless a matching unexpired owner turn is already processing accepted input. Neither queueing a follow-up nor finishing one clears an explicit pause. Ordinary productive/reconciliation admission must refuse either hold before changing generation/attempts; ordinary dispatch already requires both no explicit pause and no pending input. The existing ordinary command scheduler also skips pending-input workflows rather than repeatedly selecting an unrunnable job ahead of its peers. This skip does not consume input or supply an owner worker: productive owner ingress remains disabled, and its eventual separate selector must reauthorize the pending message and use exclusive owner-turn admission. Owner-turn claim and active native admission require an unpaused explicit control, authenticated pending input and the matching current revision/lease. Thus explicit pause blocks owner coding too; pending input alone lets only its exclusive guarded owner turn progress.

   Authenticated resume may clear an explicit pause while input remains pending, but does not apply input, bypass review/CI, clear another workflow hold or retire a runtime behind that input. Internal execution-retry/retirement scheduling is skipped while messages remain pending. Queue-created intent revisions use an input-specific progress cause, so they cannot be reported as an explicit owner resume. Status/progress distinguishes explicit pause from input waiting/processing. Processing requires the claimed turn to match the current workflow owner, generation, unexpired lease and control revision; resume cannot describe a fenced old turn as processing. The input barrier disappears only when the protected completion path applies the corresponding messages; queued peers keep ordinary automation held. Once no input remains and no explicit pause is set, normal verification may resume under a fresh guarded lease. A completed/uncertain/refused owner-turn lease cannot fall back to ordinary model admission even if its binding matches the latest checkpoint.

   If input interrupts an ordinary run, its existing run accounting returns an input-specific deferred result while retaining the checkpoint, evidence and actual model admissions. This remains deferred even when that run already spent model calls. Classification uses the original run lease's historical owner-turn identity, so the pending message required by an active owner turn does not hide that turn's provider or execution errors as an ordinary input deferral. This is reporting, not execution/recovery authority or proof of native teardown.

   Each turn owns exactly one immutable ingress `request_id` and its authenticated body, selected by `next_pending` and persisted in `workflow_owner_turn` at claim. The unchanged control revision does not include later messages in that turn. Completion atomically applies only that same request and completes only its matching turn; every later arrival remains pending, even if it shares the revision. The body dispatch captures the same request/body digest, so completion cannot consume unseen instructions. If another message remains, the next action is `process_owner_input`; otherwise it is `verify_owner_changes` under fresh ordinary admission.

   Enqueue, explicit control changes, owner claim and completion each use an immediate SQLite transaction on the same workflow store. Enqueue checks the current explicit pause/revision and matching live turn, inserts its message and conditionally advances the fence in that transaction; it never restores a pause value read before transaction admission. Claim selects and authenticates its single message while assigning its lease/revision atomically. Completion revalidates the exact request, dispatch, current lease/control and checkpoint before updating the message, turn, result, checkpoint and progress in one commit. Thus a concurrent enqueue linearizes before claim (eligible for selection) or after claim (queued behind its captured request); against completion it either leaves a peer pending before completion's pending-count projection or queues and fences afterward. Against pause it preserves the earlier pause or precedes the new explicit fence. A pause/resume that commits before completion's validation makes the old completion refuse without consuming input or rewriting the newer hold; settlement of its already-observed native outcome is still P2. Native/kernel proof acquisition keeps its existing lock ordering outside short store accesses; no SQLite transaction is retained across asynchronous native setup.

   Existing `paused=true` rows are conservatively retained as holds, including historical rows whose original cause is ambiguous. There is no migration that guesses an old pause was merely an input barrier; the authenticated owner may explicitly resume it. Resume never makes an escaped claimed/uncertain turn replayable or replaces original native closure with lease expiry. Reconciliation when owner intent changes during execution still belongs to P2: recording an already-observed outcome must preserve the newer hold and terminal state. This separation is a required protocol precondition, not implementation of P1/P2 settlement or permission to enable productive ingress.

10. Canonical acceptance metadata now has one synchronous admission boundary, separate from native setup. `WorkflowGuard::with_acceptance_metadata` checks its local lease/audit health before entering the workflow store. The store acquires an immediate SQLite transaction, validates the exact lease/binding, checkpoint, abort barriers and owner control/input admission, invokes the protected-file visitor, then revalidates using the current clock before commit. A borrowed `AcceptanceMetadata` token is created only in that transaction; production manifest creation/recovery and immutable amendment writers require it. It is neither cloneable nor serializable, does not cross a thread/async boundary, and grants no model, native, recovery or shipping capability. Fixture-only wrappers use the real store admission in disposable databases and grant no production bypass.

   Initial baseline persistence, missing-index recovery, canonical creation, amendment authority/pending/evidence/history writes, canonical replacement and completion/removal use that boundary. Replacement rechecks that the canonical manifest is still the previously observed manifest or the exact intended next manifest. Completion rechecks both the exact next manifest and original pending transaction before writing its completion and removing its pending file under one admission. Owner controls, generation changes and other metadata visitors therefore serialize with these file operations rather than committing between a separate validation and mutation. Pure `read_manifest` performs no recovery; free-sweep inspection uses it under current guard admission and refuses a missing index without creating one. A later verifier/source inspection or merge still needs its own current receipt/guard checks.

   A mutable visitor that has started and subsequently fails (including its final lease check or SQLite commit) fences the original guard and its captured dispatch/model observers. The files are retained and no further call is charged by that guard. The failure fence is recorded before releasing the shared store mutex; dispatch/model observers and queued metadata visitors recheck it after acquiring that mutex, so a callback already waiting behind the failed writer cannot charge or start work through a check made before the failure. Initial refusal before entering the visitor does not imply a file effect. Read-only inspection receives no writer token and an ordinary missing/pending-file refusal does not mark the guard as having an uncertain mutation. Existing immutable files are opened nonblocking without following symlinks, must be private current-user regular single-link files, and are compared using an exact bounded read; a FIFO or changed file refuses instead of holding the store indefinitely.

   The visitor itself acquires no native/state/session/audit locks, executes no provider/subprocess and spans no await; its trusted callers must keep those operations outside it. Native handoff, audit access and write-scope registration remain outside SQLite critical sections under their original independent services; this metadata token cannot replace their actual proof. This is serialization, not a distributed SQLite/filesystem transaction: filesystem writes are not rolled back if a later filesystem operation, commit, clock/lease recheck or controller process fails. Existing amendment/orphan evidence must remain available for exact replay. P1/P2 still must select and implement the private owner publication journal, completed-publication productive admission, supersession and authenticated process-loss settlement before any private owner publication-intent writer or consumer is introduced. In particular, canonical contract preservation on ordinary acquisition and consumers already holding an older manifest remain explicit P1 work; the new file boundary alone does not solve them.

11. Existing ordinary amendments retain their filesystem authority after an acknowledgement failure; the SQLite critical section orders access, rather than rolling file effects back. Successful initial admission authorizes only the exact independently approved amendment and its recorded baseline. A later visitor/lease/commit failure or controller death means the caller cannot infer whether those file effects happened. It grants no productive success, model replay, pause clearing or shipping authority. An entered failed mutable visitor fences the old guard; after process loss a new guard must still acquire the original native ownership through the existing service before replay. The following durable states select ordinary recovery, without another authority/model call:

   | Durable state | Ordinary reader and guarded recovery |
   | --- | --- |
   | Original manifest intact; only immutable candidate evidence exists; no pending transaction | Original acceptance stays authoritative. Retain the orphaned evidence; it does not activate a revision. |
   | Pending transaction exists; manifest is exact old or next | Productive readers and free sweep hold. A fresh authorized guard validates the original pending approval, baseline, unchanged product and exact old/next metadata, then resumes that transaction. A partial next-manifest write is never treated as an absent transaction. |
   | Exact next manifest and exact completion exist; pending still exists | Readers still hold. Guarded replay verifies the same transaction and performs the remaining idempotent completion/removal; it does not ask a model again. |
   | Exact next manifest, complete immutable evidence, original manifest-history anchor and validated exact completion exist; pending is absent | Readers may use the completed revision after their own current guard/source/candidate verification. This applies even when the prior controller never observed its success. Completion data is metadata, not a native/source execution receipt or merge approval. |
   | Revised manifest exists but completion or its original authority is absent, changed or conflicting, with no recoverable exact pending transaction | Hold and retain the bytes. Do not synthesize a completion, regenerate acceptance or silently revert to the old contract. |
   | Only original baseline exists and canonical index is absent | Free sweep refuses without mutation. Guarded original-index recovery validates the single original baseline under Decision 10; it never chooses a newer baseline by timestamp. |

   These rules apply at every ordinary evidence/history write, manifest rename, completion write and pending unlink followed by visitor failure, final admission refusal, SQLite commit failure or process loss. A pending transaction is inspected only by metadata recovery; productive reads require no pending transaction and a valid exact completion plus its original manifest-history source/base/contract/revision anchor for a revised evidence manifest. Recovery preserves explicit owner holds, budgets and original receipts. This resolves ordinary metadata visibility; it does not supply the still-blocked private-owner P1/P2 journal or its process-loss authority.

## Open threads

P1 (D/T, before any publication-intent writer): specify one admission/lock ordering for intent creation, activation, native handoff and manifest replacement. It must fence consumers already holding the previous manifest before their side effects, as well as readers arriving during publication, and identify the permitted authenticated recovery operations. A check-then-read convention is insufficient. The [proposed publication/recovery protocol](owner-publication-protocol.md) supplies a candidate ordering, schema, capability split and test exits for audit; it is not an implemented reader fence or permission to introduce the writer yet.

P2 (D/R, before any publication-intent writer): define terminal refusal/supersession and reconciliation when owner intent or candidate identity changes. Preserve all original native handoff and write-scope effects; neither deleting an intent nor leaving all readers held forever is a recovery protocol. The [proposed protocol](owner-publication-protocol.md) distinguishes metadata generations, actual native outcomes, retained invocation/continuation and explicit evidence-unavailable dispositions. Its proof-producing APIs and fault tests must be resolved and implemented before an intent is introduced; a saved plan or outcome row remains insufficient.

P3 (D/N, before productive owner consumption): define the allowlisted public projection for every GitHub body/comment/diagnostic and distinguish owner-private Discord replies from public status. Complete body text, private criteria, adapters, oracle values and model output cannot be projected by default. Until the actual output schema and all writers are covered, productive public output remains disabled.

P4 (D/V, before owner definition-correction recovery): add an independently authorized versioned correction-context transition that preserves the original immutable artifact and activation, rather than overwriting a context pathname or replaying exposed owner input. The current one-artifact-per-context rule is intentionally retained; correction-context generation and its request/history join are not implemented by this checkpoint.

P5 (D/storage, before enabling productive owner preparation): specify and enforce aggregate protected-artifact storage admission and reference-aware retention for unactivated preparations as well as activated artifacts. A completed artifact remains immutable and cannot be automatically deleted while input, activation, body dispatch, native reconciliation or a retained recovery/rollback reference may need it. The current producer has a 4 MiB per-file limit and one artifact per context, but no aggregate preparation quota or reclamation protocol; the 128 MiB activation-history limit does not bound unactivated files. Current productive owner ingress remains disabled, and test artifacts live in disposable fixture namespaces. Do not invent an existing quota, evict an artifact to admit a retry, or override managed storage floors. The carrying cost is an explicit storage reservation/retention join before enabling the producer, rather than a later cleanup job guessing which original evidence is live.

Canonical publication, interrupted native handoff/recovery, actual owner worker ingress and P1–P5 remain blocking work. Final C source/artifact freshness and storage-aware original quiescence remain required independently. No product requirement or acceptance criterion is cut by this staging.

## Explicit pause and pending-input checkpoint — 2026-11-06

Two behavioral regressions first reproduced an explicit pause permitting a new owner turn and pending input preventing an authenticated explicit resume. The explicit pause flag and derived pending-input barrier now have separate meanings. Ordinary productive/reconciliation admission, ordinary dispatch and ordinary acceptance binding respect both barriers; an owner turn requires pending authenticated input, an unpaused control and its exact current revision.
