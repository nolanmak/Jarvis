# Owner acceptance publication and recovery

Owner: D/#1713 and T/#1712, using the existing workflow, native ownership and private verifier services. This is an implementation checkpoint, not a completed handoff or permission to enable productive owner coding. Epic #1703, private-verifier D1–D8 and original owner holds remain binding.

## Decisions

1. An independently prepared acceptance artifact must be durable before workflow activation. Its private `Stored` record contains the complete original owner input context, proposal, protected adapter map, registered contract and actual intended-red baseline receipts. The existing input-context hash selects `owner-preparations/<context_sha256>.json`. There is exactly one immutable completed artifact per context: creation uses `persist_noclobber` and directory fsync; an existing artifact is reused only after exact input and protected registration validation. A conflicting write refuses and retains the old bytes, including on concurrent acknowledgement loss. Once a completed artifact is durable, no retry regenerates or overwrites it. Before that boundary, the producer reuses the existing `scope_authority::persistent_revision` completed-response journal; baseline reproduction and unpersisted provider responses may repeat only under the existing workflow/native admission, actual call accounting and bounded budgets. This is not an exactly-once inference claim. Concurrent producers cannot overwrite a winner: a no-clobber loser returns failure and a subsequent retry reopens the saved winner. A lost/uncertain native outcome still requires original native reconciliation before further dispatch; an absent artifact is not quiescence evidence. These read-only preparation retries never authorize repeating an exposed owner coding body. An independently authorized definition correction needs a distinct versioned context/transaction; that owner-correction join remains blocked work below. The producer returns the exact private file's identity, not only an in-memory proposal. This prevents a later recovery from guessing which proposal was activated.

2. Every new private activation carries a version-1 preparation binding with exactly `version`, `artifact_sha256`, `context_sha256`, `registration_sha256` and `baseline_receipts_sha256`. The artifact is at most 4 MiB, a current-user-owned regular single-link file with no group/world permission bits (created as 0600), opened with `O_NOFOLLOW|O_NONBLOCK`; its bytes must equal `serde_json::to_vec(Stored)` after parsing. `artifact_sha256` hashes those exact bytes. `context_sha256` uses the existing `Input::key` (`SHA256(serde_json::to_vec(Input))`). The registration and complete receipt vector hashes use `native_vm::ownership::canonical_bytes(serde_json::to_value(value))`, the same canonical encoding as existing ownership and baseline history. Vector order is retained. Every digest is lowercase 64-character SHA-256. Unknown fields and unsupported versions refuse. The registered metadata already binds adapter paths and content hashes; its existing `verify_files` still checks the actual protected byte map. These digests are binding data, not independent activation, cleanup or shipping authority. The guard still authenticates the current owner request, candidate, pause revision, source, previous contract, native store and generation.

3. Private activation writes its preparation binding and complete baseline receipts to `workflow_owner_preparation(request_id PRIMARY KEY REFERENCES workflow_owner_revision(request_id), record TEXT NOT NULL, receipts TEXT NOT NULL)` in the same SQLite transaction as the existing activation, checkpoint, review invalidation and generation fence. `record` is the binding above (maximum 4096 bytes); `receipts` is the complete `VerifierReceipt` vector (maximum 4 MiB). The existing `owner_acceptance_registered` or `owner_contract_revised` event carries the identical binding in optional `preparation`; its existing event limit remains 32 KiB. History validation uses parsed-value/reserialized-value equality as well as strict schemas, joins both directions, verifies the registration digest and intended-red baseline, and rejects one-sided missing, changed or orphaned projections. A missing pair remains unproven legacy-shaped inspection metadata under Decision 4. Preparation data counts toward the existing 128 MiB / 1024-activation history bounds. Initial and revised private acceptance both retain their full baseline receipts. Acknowledgement loss must not create another activation or replenish any budget.

4. Replay compares the exact preparation binding and baseline, in addition to the existing original request, body digest, previous/next contracts and binding. Reopening the database changes none of these identities. Old activation events without preparation bindings remain historical metadata; no binding or private file may be synthesized for them. There is no timestamp/version cutoff that grants missing preparations legacy execution authority: every activation without its original preparation is unproven for productive owner admission, including a new activation damaged to look legacy by removing both event preparation and its projection. Read-only history inspection can retain that legacy-shaped metadata; this is explicitly not proof that all new-history damage is distinguishable from legacy records. Both first-builder and continuation paths now require the original producer's opaque preparation through Decision 8. `has_owner_acceptance_for_turn` checks intact private preparation history, rather than revision existence; this boolean is inspection data, not the productive capability. P1 must still add completed-publication admission before enabling the consumer. Reopening the database cannot upgrade missing preparation metadata. A contract hash alone is insufficient.

5. The next stage is a protected publication intent that binds this receipt to the prior canonical manifest and the exact next manifest/evidence file. Publication occurs only after the original-store native handoff and registered write-scope update succeed. Every ordinary manifest consumer must hold while an unresolved publication intent exists. Replay must check the original artifact bytes/context, activation history, current owner intent, unchanged candidate and complete previous-or-next manifest before any write. Immutable evidence/history, manifest replacement, completion persistence and pending deletion need fault tests at every acknowledgement boundary. The existing canonical namespace and manifest remain the only acceptance source; this adds no alternate verifier engine or verdict store.

6. A claimed owner turn does not become replayable because its process disappeared or lease expired. Recovery after process loss needs authenticated original native closure and a guarded ownership transfer before it can finish publication. The current claim API intentionally refuses claimed/uncertain turns; publication recovery must not bypass that rule, clear a pause, replay an exposed body, invent a conversation, or reuse an old generation. D/R own that recovery join before productive worker ingress is enabled.

7. Newly saved preparation envelopes use `Stored { version: 2, input, candidate, prepared }`. `Input` and its version-1 context key remain unchanged. Physical candidate identity is deliberately outside that key: replacing a checkout must find and refuse the original context artifact, rather than select a new filename and regenerate acceptance for the same request. The envelope and every nested candidate record reject unknown fields. A cached artifact without the version-2 envelope or original candidate identity refuses in place; the producer never fills in identity, overwrites the file or falls through to a paid preparation. Recovery of older/unversioned envelopes needs an independently authorized migration/rebinding protocol before productive recovery; no automatic compatibility path is claimed.

   `candidate` has exactly `version: 1`, `root`, `git_pointer`, `git_directory`, `common_pointer` and `common_directory`. Each directory contains canonical absolute `path`, filesystem `device`, `inode` and `uid`. Each nullable pointer contains its absolute `path`, `device`, `inode`, `uid` and lowercase SHA-256 of its exact bytes. The root, actual Git administration directory and actual common directory must be owned directories; symlink leaves refuse. For linked worktrees the `.git` file and optional `commondir` file are opened with `O_NOFOLLOW|O_NONBLOCK`; each must be current-user-owned, regular, single-link and at most 4096 bytes. Pointer bytes must be UTF-8. Zero or more terminal LF bytes are removed for target parsing only; no other whitespace is trimmed. The remaining Git pointer must begin with exact `gitdir: ` and have a nonempty target; a common-directory pointer is the nonempty path itself. Any remaining NUL, LF or CR refuses, including CRLF framing. Repeated terminal LFs are allowed framing, remain in the hashed original bytes and therefore cannot be added to an existing saved pointer identity. Relative targets resolve against their containing directory. Captures recheck directory identities and pointer bytes after traversal. Ordinary product edits do not change this identity; Git metadata copying/replacement, aliases to a different physical checkout and changed pointer bytes do.

   The producer captures identity before independent preparation and rechecks it on cached reload, before saving and before activation. The owning guard rechecks the exact artifact after asynchronous inspection, across native settlement and around write-scope registration. The artifact digest already retained by the activation transaction consequently binds this candidate data too. This is point-in-time physical binding data, not repository/workspace authorization, original native closure, a held directory capability or source-content/freshness evidence. P1/P2 still require authenticated provenance and original locked native/storage proof across their actual mutation boundaries. A replacement checkout cannot be authorized merely by recomputing this record or by restoring the same commit at the same path. Recovery must locate the original saved input-context key through immutable lineage; deriving a fresh key from a later recovery lease would incorrectly evade the original artifact. Device/inode snapshots do not solve inode reuse after deletion; original locked native/storage and workspace provenance remain independent requirements.


8. Productive owner-body APIs take the original `Arc<PreparedOwnerAcceptance>`, not a reconstructed `PreparedAcceptance`. The producer rechecks its exact private artifact, physical candidate, original request/body/owner/pause/source/head and the single guarded activation generation (`original + 1`); the current store must retain the identical preparation binding for that turn. This generation rule deliberately does not authorize process-loss recovery: P2 must supply immutable original-input lineage before any later recovery generation can pass. Both first-builder and continuation reservations require the binding in their SQLite transaction. First-builder reservation additionally retains the existing original locked `UnusedNativeOwnerProof` and all baseline/cleanliness/attribution checks. The old preparation-free continuation reservation is compiled only for metadata fixtures; the preparation-free first-builder wrapper is removed.

   The existing version-1 owner-body `Record` gains optional `preparation: OwnerPreparationBinding` for historical parsing; every new production reservation writes `Some(original_binding)` into both the dispatch row and its identical `owner_body_dispatch_started` event. History with a preparation must still join to its intact original activation/projection and baseline. A missing field on old history is descriptive only. A saved row cannot reconstruct `OwnerBodyDispatch`, whose constructor remains the once-only factory. The live non-cloneable dispatch instance is shared by reference with the original opaque preparation in `OwnerBodyAdmission`; shared references do not create another reservation or permit replaying the prompt.

   After reservation and before calling a provider, the guard narrows its dispatch and model-accounting observers to that captured admission. The callbacks retain it across thread hops and after body success/failure; absence of task-local context never restores ordinary admission. Dispatch revalidates the artifact and exact persisted reservation. Model admission also checks the actual native provider and builder attribution, then validates current lease/turn/pause, original preparation and captured reservation in the same immediate SQLite transaction as existing model attribution, bounded budgets and resource charging. Even if both the saved dispatch and its event lose the new field and look legacy-shaped, they differ from the captured original reservation and fail. Refused artifact/activation/provider/turn checks and failed audit persistence leave model and bounded-attempt charging unchanged. Original owner pause, pending input and merge accounting remain unchanged. Completion still requires the fresh original native completion capability; a reserved/charged model or reply is not completion, publication, owner resume or shipping authority.

   This supplies original-preparation/body admission, not P1's canonical publication gate, native source execution proof or P2 recovery. Metadata fixtures and observer calls do not prove live provider/VM execution. Productive worker ingress remains disabled until those separate requirements and public-output protection are connected and verified.

## Testable exits

First capture the exact private preparation in activation history and cover actual guard activation, revised-baseline retention, changed-artifact replay, missing/changed projection, lost audit writes and database reopen. Then implement the protected manifest transaction and all-reader hold/replay. Finally connect authenticated process-loss recovery and productive owner consumption with private/public output separation. Each stage needs its own evidence; a preparation receipt alone does not prove manifest publication or live Discord coding.

## Open threads

P1 (D/T, before any publication-intent writer): specify one admission/lock ordering for intent creation, activation, native handoff and manifest replacement. It must fence consumers already holding the previous manifest before their side effects, as well as readers arriving during publication, and identify the permitted authenticated recovery operations. A check-then-read convention is insufficient. This is unresolved protocol design and blocks manifest implementation/handoff, not a completed reader fence.

P2 (D/R, before any publication-intent writer): define terminal refusal/supersession and reconciliation when owner intent or candidate identity changes. Preserve all original native handoff and write-scope effects; neither deleting an intent nor leaving all readers held forever is a recovery protocol. The exact evidence that can release that hold must be selected and tested before an intent is introduced.

P3 (D/N, before productive owner consumption): define the allowlisted public projection for every GitHub body/comment/diagnostic and distinguish owner-private Discord replies from public status. Complete body text, private criteria, adapters, oracle values and model output cannot be projected by default. Until the actual output schema and all writers are covered, productive public output remains disabled.

P4 (D/V, before owner definition-correction recovery): add an independently authorized versioned correction-context transition that preserves the original immutable artifact and activation, rather than overwriting a context pathname or replaying exposed owner input. The current one-artifact-per-context rule is intentionally retained; correction-context generation and its request/history join are not implemented by this checkpoint.

Canonical publication, interrupted native handoff/recovery, actual owner worker ingress and P1–P4 remain blocking work. Final C source/artifact freshness and storage-aware original quiescence remain required independently. No product requirement or acceptance criterion is cut by this staging.

## Ordinary recovery admission checkpoint — 2026-11-06

The owner-turn claim API already refused an interrupted claimed/uncertain turn, but ordinary `claim` could increment its workflow generation after lease expiry. A separate controller could therefore strand the original turn before authenticated recovery. The new database-reopen regression reproduced this takeover before the fix. All ordinary claim purposes now refuse an owner turn without a recognized `completed` or `setup_refused` disposition, in the same immediate transaction and before changing generation, attempts or events. The regression covers claimed, uncertain and unknown dispositions, preserves checkpoint/input/control/accounting, and confirms an unrelated productive workflow can still acquire its lease. Ordinary recovery callers, including outside-target settlement and missing-publication-checkout recovery, receive the existing deferred result rather than taking that generation.

This closes ordinary lease takeover, not P1/P2 or process-loss recovery. A future authenticated recovery API still needs original native closure, a new recovery generation and immutable lineage; it cannot use ordinary claim, rewrite the activation fence or relabel an escaped turn unstarted. Registration itself uses `INSERT ... ON CONFLICT DO NOTHING` and does not replace an existing binding. After ownership is settled, normal acquisition can still checkpoint changed inputs, so that path and already-loaded manifests must participate in the eventual publication fence. `original_manifest` can also create a missing index from an orphan baseline; its recovery writes, amendment activation and candidate-receipt reads belong to the same publication protocol. No pending-publication writer or recovery bypass is introduced here.

The final production CLI compile check also passed. Commands, red/green results and limits are recorded in `1703-owner-claim-fence-proof.json`.
